The logic of HTTP caching.

Caching is not simply saving a copy. It is a set of rules for deciding when previously received content may be reused.

Why caches exist

Fetching a resource again can cost network time, server processing and bandwidth. HTTP caching allows a client or intermediary to reuse a stored response when doing so is permitted. A browser cache may store resources for one user's visits. A shared cache, such as one at a content delivery network (CDN), may serve multiple users.

These caches are not interchangeable. A page with private account data may be acceptable in a browser's cache but inappropriate for a cache shared between visitors. Correct response directives determine the difference.

Freshness and Cache-Control

A cache uses HTTP metadata to determine whether a stored response is fresh and can be reused without contacting the origin. The Cache-Control header communicates reuse and storage rules.

DirectiveWhat it expresses
max-age=600Permits freshness for up to 600 seconds under the applicable cache rules.
no-cacheStored responses require successful validation before reuse.
no-storeCompliant caches must not store the response.
privateThe response is intended for private rather than shared caches.
publicExplicitly allows shared-cache storage when otherwise eligible.
s-maxage=120Overrides freshness calculation for shared caches.

The header Cache-Control: public, max-age=600 can work well for a shared, unchanging asset. It is not a safe default for every API or personalized page.

Validation with ETag and Last-Modified

When a cached response becomes stale, the cache may ask the server whether its stored representation is still current. An ETag is a validator associated with a representation. A client can send it back in an If-None-Match request header.

A Last-Modified timestamp can also be used with If-Modified-Since. Validators have different precision and strength characteristics; application requirements determine which is suitable.

COMMON MISUNDERSTANDING

A 304 Not Modified response is not a server error. It is a successful conditional response that normally has no representation body and supports reuse of previously stored data.

The complications of shared caching

Shared caches have to determine not only when a stored response is fresh, but also which requests can reuse it. A cache key often includes the method, scheme, hostname and request target. Responses using the Vary header identify request fields that affect response selection, such as compression preferences.

Cookies and authorization introduce additional constraints. A response that varies by signed-in user must not accidentally be returned to another person. Cache rules for authenticated responses are more nuanced than a simple "cache on" switch.

Using a CDN also does not guarantee a performance improvement for every request. Origin distance, object size, cache-hit rate, TLS setup and other factors influence the result.

Inspect what the server actually sends

Start by reading the response headers. In addition to Cache-Control, look for ETag, Last-Modified, Vary and sometimes Age.

TERMINAL / EXAMPLE
curl -I https://example.com/

To test an ETag-based conditional request, first obtain the exact validator returned for your target resource. Then send it back in a subsequent request:

TERMINAL / EXAMPLE
curl -i -H 'If-None-Match: "example-etag"' https://example.com/

The validator in this command is illustrative; replace it with a value actually returned by the server. You should not expect a 304 unless the representation matches the supplied validator and the server supports that conditional exchange.
