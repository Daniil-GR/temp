Reading HTTP responses.

A response code is a summary, not a diagnosis. Learn to read the rest of the message before deciding what went wrong.

The anatomy of a request and response

HTTP is an application-layer protocol built around requests and responses. A request includes a method, target and header fields, and may include content. The response contains a status code, header fields and, when appropriate, a message body.

For example, a browser might request a document with GET /. The server can answer 200 OK and identify the response format using Content-Type: text/html. Other fields can describe caching, content encoding or redirects.

Methods describe the requested action

The HTTP method expresses what the client wants to do. GET requests a representation of a resource. HEAD requests metadata corresponding to GET without transferring the response content. POST submits data for processing; PUT replaces or creates the target resource according to its defined semantics; and DELETE requests removal of the association with a target resource.

Methods have additional properties. A method is called safe when its defined semantics do not request a state change; GET and HEAD are safe. A method is idempotent when repeating the same request has the same intended effect as making it once. These properties guide retry behavior, although an implementation can still perform incidental activities such as logging.

WHY HEAD IS NOT A COMPLETE HEALTH CHECK

A HEAD request may produce a different result from GET on some applications. It is a convenient quick test for headers, but confirming that a page actually renders requires fetching its content.

The five status-code families

RangeMeaningExample
1xxInformational or interim response100 Continue
2xxSuccessful handling200 OK, 204 No Content
3xxRedirection or related action301 Moved Permanently
4xxClient-related error class404 Not Found, 429 Too Many Requests
5xxServer-related error class500 Internal Server Error, 502 Bad Gateway

The first digit is a useful classification, not a complete root-cause analysis. In practice, a 404 can result from a missing file, an incorrect application route or a reverse-proxy rule that selects the wrong service.

Why 502 and 504 are different

Reverse proxies and gateways often sit between a client and the application server. A 502 Bad Gateway means a gateway or proxy received an invalid response from an upstream server. A 504 Gateway Timeout means the gateway did not receive a timely response from an upstream server it needed to complete the request.

Both can involve upstream trouble, but the codes describe different observations. Start by checking whether the gateway can resolve and connect to the upstream, whether the application is serving requests, and whether timeout thresholds are appropriate.

A 503 Service Unavailable is different again: it indicates that the server is currently unable to handle the request, often because of temporary overload or maintenance. A Retry-After header can provide a suggested delay when the server supplies one.

Headers worth knowing

Headers provide context that the status code cannot convey alone. Content-Type identifies the media type; Content-Encoding identifies content codings such as gzip or br; Location supplies a redirect destination; and Cache-Control tells caches how they may store and reuse a response.

Response header names are case-insensitive. Their specific values, however, have syntax and semantics defined by the relevant specifications.

TERMINAL / EXAMPLE
curl -sS -D - -o /dev/null https://example.com/
curl -sS -L -I https://example.com/

The first command displays response headers while discarding the content body. The second follows redirects and shows headers from the requests involved. To diagnose a real incident, inspect the requested hostname and path, resolve DNS separately, confirm TLS, and then compare response headers with application logs.
