How HTTPS establishes trust.

HTTP and the protected connection

HTTP defines the messages used to request and deliver web resources. HTTPS is HTTP over a transport protected using Transport Layer Security (TLS). The protection aims to prevent observers on the network from reading or silently altering application data and to authenticate the server.

For a typical HTTPS connection over TCP, a browser establishes a TCP connection and performs a TLS handshake before sending ordinary HTTP messages. HTTP/3 uses QUIC, which incorporates TLS 1.3 differently, so that specific TCP sequence is not universal.

Inside a TLS 1.3 handshake

A TLS handshake negotiates the security parameters that both sides will use. In TLS 1.3, the client begins with a ClientHello containing supported cryptographic options and key-exchange information. The server responds with a ServerHello selecting compatible parameters.

The peers use their key shares to derive shared traffic secrets. The server presents authentication information, normally including its certificate chain and a cryptographic signature proving possession of an appropriate private key. After the handshake has been verified, protected application data can flow.

  1. Agreement: the peers establish compatible cryptographic parameters and key material.
  2. Authentication: the client checks the server certificate and associated handshake proof.
  3. Protection: application messages use session keys derived for the connection.

TLS 1.3 reduces the number of handshake round trips compared with earlier versions, but network distance and application behavior still influence the experience.

What certificate validation checks

A certificate binds a public key to identifying information, including permitted DNS names. Modern browsers check that the requested hostname appears in the certificate's Subject Alternative Name (SAN) extension, that the certificate is within its validity interval and that the issuing chain can be linked to a trusted root under the browser's policy.

For example, a certificate valid only for www.example.com does not automatically cover api.example.com. A wildcard such as *.example.com can cover direct subdomains under typical hostname-matching rules, but not arbitrary levels beneath them.

WHAT A PADLOCK DOES — AND DOES NOT — MEAN

HTTPS protects a connection to a validated hostname. It does not independently verify whether the website's articles, commercial claims or downloadable files are trustworthy.

Browsers and operating systems also apply policies around revoked certificates, certificate transparency and transport security. Exact behavior can differ by platform and certificate type.

SNI, ALPN and shared servers

A single IP address may host many HTTPS websites. The client can supply a hostname in the TLS Server Name Indication (SNI) extension so the server can select an appropriate virtual host and certificate. Ordinary SNI is visible in the ClientHello on conventional TLS connections; newer Encrypted ClientHello (ECH) mechanisms aim to protect more of that information when supported.

Application-Layer Protocol Negotiation (ALPN) is different: it indicates which application protocol should be used inside the secure connection, such as http/1.1 or h2. ALPN does not select the domain, and SNI does not replace certificate validation.

Inspect a real HTTPS connection

The curl command can reveal the negotiated TLS version, certificate verification outcome and HTTP response. The flags below are suitable for publicly available demonstration websites.

TERMINAL / EXAMPLE
curl -Iv https://example.com/

Use -I to request headers and -v for connection diagnostics. If the certificate is invalid, do not use -k as a routine fix; that flag disables important verification.

To inspect a presented certificate chain using OpenSSL, connect with a matching SNI hostname:

TERMINAL / EXAMPLE
openssl s_client -connect example.com:443 -servername example.com -showcerts

This command displays handshake details and certificates, but do not assume that merely printing certificates performs every validation step a browser would apply.
