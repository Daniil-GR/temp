Understanding DNS.

From a name in the address bar to an IP address: the lookup process, the records involved and the reasons DNS changes sometimes take time.

What DNS is responsible for

The Domain Name System (DNS) is a distributed naming system. It stores structured records that allow applications to discover addresses and other information associated with domain names. When someone enters example.com into a browser, the browser ultimately needs an address it can connect to.

DNS answers that naming question; it does not establish the network connection, verify that a website is healthy or guarantee that a returned address is reachable. A site can resolve correctly while its server is offline.

This distinction is useful in troubleshooting: a failed DNS lookup and a failed TCP or TLS connection require different investigations.

Resolvers and authoritative answers

Most devices use a recursive resolver supplied by a network, configured manually or offered as part of an encrypted DNS service. A resolver tries to answer from its cache first. If it needs fresh information, it can follow the DNS hierarchy.

  1. The resolver discovers which servers are responsible for a top-level domain, such as .com.
  2. It follows the delegation toward the authoritative name servers for the requested zone.
  3. An authoritative server supplies the records it is responsible for, or indicates that the requested name or record does not exist.
  4. The resolver returns an answer to the client and may cache it, subject to applicable rules.

The resolver does not generally contact the entire hierarchy for every query: caching avoids repeated work. The result returned to a browser may also be influenced by local host files, operating-system caches and network policy.

One subtlety: a normal CNAME record cannot coexist with unrelated record data at the same owner name under standard DNS rules. Some DNS providers implement flattening features to make apex-domain configuration more convenient; those features are not ordinary CNAME records.

TTL, caching and changes

DNS responses include a time to live (TTL), which tells caching resolvers how long record data may be reused. An A record with a TTL of 300 seconds may remain in compliant caches for up to five minutes after the response is obtained, though local policy, caching layers and queries made at different times can produce different observations.

PRACTICAL EXAMPLE

If an A record was cached just before you changed it, a resolver may continue serving the previous address until that cached response expires. Lowering a TTL only after the old record has already been cached does not retroactively shorten its lifetime.

Negative answers can be cached too. That is why creating a previously nonexistent hostname can still appear delayed to some users even when the new record is already visible at the authoritative server.

A small DNS investigation

The dig command is a useful starting point on Unix-like systems. Test the public documentation domain rather than assuming that your own service must return a particular value.

TERMINAL / EXAMPLE
dig example.com A +noall +answer
dig example.com AAAA +noall +answer
dig example.com NS +short

The first two commands show address records and the remaining TTL as seen by the resolver. The third lists name-server records. To ask a specific recursive resolver, prefix a query with its address:

TERMINAL / EXAMPLE
dig @1.1.1.1 example.com A +noall +answer

Compare answers only after checking the record type, resolver and remaining TTL. A difference does not automatically indicate an attack or malfunction.

Do not confuse resolution with reachability

Once a name resolves, test network connectivity separately. An HTTPS request can fail because of TLS validation, firewalls, routing, a closed port or an unhealthy web service even when DNS is correct.
